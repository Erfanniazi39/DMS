# Business System — Data Model

Internal reference for Alish Automation's Business System schema: what tables exist, what fields they carry, and how they relate. This document mirrors the [interactive diagram](https://claude.ai/artifact/GaJCEU3MsXCyatuKD5aC3Z) field-for-field — treat the diagram as the visual companion to this file, not a separate source of truth.

The system is organized into four parts:

- **Master Data** — reusable entities that get referenced, not created fresh each time (Supplier, Employee, Department, Customer, Unit, Item, Item Category).
- **Transaction** — the business events themselves, split into **Purchases** and **Sales**.
- **Users & Access** — who can log in, what they're allowed to do, and what they did.
- **Inventory** — stock levels and the movements that changed them.

Field types, choice lists, and FK delete rules are proposed to match the codebase's existing conventions (Persian UI labels, Decimal money fields, Jalali-display dates stored as Gregorian, `PROTECT`/`CASCADE`/`SET_NULL` conventions). Table and field names given directly by you are kept as specified — nothing renamed or redesigned beyond what's noted below.

## Users & Access — کاربران و دسترسی

`status` is pulled out as an enum; roles and permissions are real tables joined through `Role_Permission` rather than a fixed list on the role itself, so one permission can belong to several roles without duplicating rows.

**User and Employee are independent entities. There is no relationship between them — no `User.employee` field, no `Employee.user` field, nothing joining the two tables.** A User is a login account for the system (username, password, role, status, email, phone). An Employee is a Master Data business record for a person who works at the company (name, department, position, hire date, etc.). Creating one never creates or requires the other: an Employee can exist with no User account, and a User can exist with no corresponding Employee record. This was previously implemented as a required 1:1 `User → Employee` link; that link has been removed by request and must not be reintroduced without an explicit new instruction.

## Inventory — انبار / موجودی

Stock holds a running balance per item/location; Stock Movement is the ledger of everything that changed it. Both key off Item and Location rather than owning their own copies of that data.

### Stock — موجودی

| Field | Type / Notes |
|---|---|
| `id` | AutoField |
| `item` | FK → Item, `PROTECT` (Master Data) |
| `location` | FK → Inventory Location, `PROTECT` |
| `quantity` | DecimalField(12,2) — running balance for this item/location pair |

### Stock Movement — گردش موجودی

| Field | Type / Notes |
|---|---|
| `id` | AutoField |
| `item` | FK → Item, `PROTECT` (Master Data) |
| `location` | FK → Inventory Location, `PROTECT` |
| `movement_type` | FK/choices → STOCK_MOVEMENT_TYPE |
| `quantity` | DecimalField(12,2) |
| `movement_date` | DateField |
| `reference_type` | CharField(30) — **open**, not a real FK yet |
| `reference_id` | IntegerField — **open**, not a real FK yet |
| `note` | TextField, blank allowed |

**Open:** `reference_type` / `reference_id` read like a generic pointer back to whatever caused the movement (a Purchase Item, a Sales Item, a manual adjustment). Left as a plain type/id pair rather than real foreign keys, since a single column can't target more than one table and the valid types haven't been specified yet.

- **Audit_Log's `action`, `entity_type`, `details`** — intentionally left open until the Purchases/Sales/Document workflow is finalized.
- **Purchase Item vs. Sales Item** — Purchase Item stores its item as free text (`name`); Sales Item links to the Item table. Confirm whether Purchase Item should also link to Item.
- **Sales Document's `document_type`** — assumed to reuse Purchases' `DOCUMENT_TYPE` enum; not explicit in the original spec.
- **Customer** — no Status or Bank Information fields yet, held back for a later update.
